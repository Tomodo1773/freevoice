# ADR 0001: 録音制御を単一ジョブ所有モデルにする

- 日付: 2026-07-15
- ステータス: 採用
- 関連PR: #94（それ以前の試行: #86, #88, #93 など）

## 背景

録音制御（Push-to-Talk の開始〜文字起こし〜整形〜貼り付け）は、状態遷移の複雑さが原因で
「予期せぬ不具合 → パッチ → さらに複雑化」を繰り返していた。ステートマシンの再設計にも
何度か挑戦したが、そのたびに不具合の再発とコードの肥大化で頓挫した。

根本分析の結果、原因は状態の「分類」ではなく、**非同期プロセスとリソースの「所有」** に
あると結論づけた。

1. **遷移が瞬間ではなくプロセスだった。**「開始」は config 読込 → デバイス検証 →
   getUserMedia → セッション確立という数百msの非同期プロセスで、各 await の合間に
   キーエッジ（押下/解放）や認識エラーが割り込める。同期的な reducer の遷移表では
   この「遷移の途中」を表現できない。
2. **開始処理がキーエッジごとに並行して走れた。** そのため各 await 地点で epoch を
   採番して「自分は追い越されていないか」を自己申告し、追い越されていたら掴んだ
   リソースを自分で片付けて降りる、という規約で衝突を防いでいた（Overlay.tsx に
   supersede チェックが5箇所）。await を1つ増やすたびに新しい競合パターンと後始末が
   1つ増える構造だった。
3. **状態とリソースの所有が分離していた。** 本当の状態は reducer の phase だけでなく、
   7つの ref（session/abort/epoch...）、TranscriptionSession 内部の再接続ステート、
   OS側のミュートとウィンドウ表示に分散していた。「phase は error だが session は
   生きている」「ミュートが残る」という不整合が構造的に可能で、実際のバグは
   ほぼすべてこの穴から出ていた。
4. **表示と制御が同じマシンに同居していた。** done/error/nospeech のフェードタイマー
   （hideRequest の世代管理）が制御状態と絡み、状態数とガードが掛け算で増えていた。
5. **テストが問題の易しい側しか守れなかった。** reducer の同期遷移テストは書けるが、
   バグの温床である「await をまたぐタイミング競合」は検証できなかった。

## 決定

制御を「状態の分類」ではなく「所有」で設計する。

1. **アプリに録音ジョブは常に最大1つ**（`recorder.ts` の `RecorderController`）。
   キーの押下/解放は判断せず受付係の一点に集約する。
   - 押下: ジョブが無ければ開始。処理中（transcribing/formatting）なら中止。
     開始中・録音中は無視。
   - 解放: 走っているジョブに停止シグナルを送るだけ。
2. **録音1回の一生を、上から下に読める1つの流れにする**（`RecordingJob.run`）。
   マイク・ミュート・セッションの解放はすべて try/finally に置き、成功・失敗・
   キャンセルのどの経路でも必ず実行する。不整合を規律ではなく構造で防ぐ。
   開始処理全体には1つの絶対期限を設け、タイムアウト後に遅れて取得されたリソースも
   disposer で回収する。セッションは開始完了を await する前からジョブが所有する。
3. **キー解放と認識エラーは単一の停止シグナルで待つ。** 開始処理中に解放が来ても
   シグナルが保持され、確立後にそのまま処理へ進む（旧 stop-pending の置換）。
4. **表示は制御から分離する**（`overlayView.ts`）。done/empty/error は「数秒表示して
   フェードするトースト」として扱い、linger/fade タイマーとウィンドウ表示/非表示を
   表示ストアが一手に所有する。終端表示はジョブのリソース解放後に行い、ログ保存などの
   非クリティカルな後処理は次の録音開始を塞がない。
5. **副作用はすべて注入する。** タイミング競合（開始中の解放、処理中の再押下、
   開始タイムアウト等）を DOM/Tauri なしの単体テストで検証できるようにする。

あわせて、体感差のほぼない2点だけ仕様を変えた。

- 開始処理中にキーを離した場合、停止を予約せず確立後そのまま処理へ進める
  （録音実体がほぼ無いので、従来どおり空結果表示に落ちる）。
- 開始停滞からの「押し直しによる救出」をやめ、4秒タイムアウトで自動エラーにする。

## 根拠

- 同時に走るジョブが存在しなければ、「追い越し」という問題自体が消える。
  epoch・supersede チェック・居残りセッション掃除は対処でなく不要になる。
- リソースの取得と解放が同じ関数の try/finally で対になっていれば、
  「状態とリソースの不整合」はコードレビューの注意力に依存しない。
- 過去のリファクタリングが頓挫したのは、状態の名前を整理しても複雑さの実体
  （await の合間の競合と後始末）が遷移表の外に残り続けたから。所有を変えない限り
  同じ経路で失敗すると判断した。
- 制御が普通の TypeScript クラスになったことで、従来テスト不能だった競合シナリオが
  vitest の単体テストで固定できるようになった（recorder.test.ts / overlayView.test.ts）。

## 影響

- Overlay.tsx + overlayReducer.ts に集中していた録音制御を、recorder.ts（所有と制御）/
  overlayView.ts（終端表示）/ Overlay.tsx（副作用の接続と描画）へ責務で分割した。
- 今後、録音フローに手を入れるときは次を守る。
  - 録音に関わる新しいリソースは RecordingJob 内で取得し、解放を finally に置く。
     非同期取得には開始期限と、遅延解決時の disposer を必ず組み合わせる。
  - 新しい外部イベントは RecorderController（または停止シグナル）に集約し、
    ジョブの外から phase やリソースを直接触らない。
  - 表示の新しい状態はまず OverlayView 側で表現できないか検討する。
    制御（JobPhase）に状態を増やすのは最後の手段。
- Azure Speech の再接続ロジックは TranscriptionSession 内に閉じたまま維持する。
  外への通知は「停止シグナル（認識エラー）」の1本のみ。
