# ADR 0002: キャンセルを Esc の低レベルキーボードフックで受ける

- 日付: 2026-07-16
- ステータス: 採用
- 関連: ADR 0001（決定1の「押下: 処理中なら中止」を本 ADR で改める）
- 関連ブランチ: `feature/esc-cancel-hook`（cda2219。ADR 0001 のリファクタを先に通すため棚上げしていた先行実装。フックはここから引き継いだ）

## 背景

キャンセルの入力が PTT ホットキー（`Ctrl+Shift+Space`）の再押下だった。つまり同じキーが
開始・停止・キャンセルの3役を兼務しており、キーエッジが1つ紛れ込むだけで意図しない
キャンセルが成立する。役割の兼務そのものが誤爆の構造的な原因だった。

Esc への変更は以前にも検討して見送っている。ただしそれは `RegisterHotKey`
（`tauri-plugin-global-shortcut`）を前提にした判断だった。この方式は登録している間 Esc を
常時横取りするため、アイドル中も他アプリの Esc が死ぬ。回避のために「処理中だけ動的に
登録・解除する」と、登録失敗やタイミング競合の面倒を新たに抱え込む。

## 決定

Esc を `WH_KEYBOARD_LL` の低レベルキーボードフックで受ける。フックはキーごとに
「消費する / 素通しする」を選べるので、キャンセル可能なとき **だけ** Esc を消費し、
それ以外は `CallNextHookEx` で素通しできる。動的な登録・解除は要らず、フックは起動時に
1回張るだけでよい。

1. **入力を3つの intent に分ける。** START（PTT 押下）/ STOP（PTT 離上）/ CANCEL（Esc）。
   PTT からキャンセル役を剥がし、ジョブがあるときの押下はフェーズを問わず無視する。
2. **キャンセルの意味は変えない。** 従来どおり処理中（transcribing / formatting）のみ。
   starting / recording 中の Esc はキャンセル可能ですらなく、他アプリへ素通しする。
3. **フックは自分で武装解除する。** Esc を1回消費したら、フロントの応答を待たずに
   `CANCELABLE.swap(false)` でその場で disarm する。フックが Esc を奪うのは
   「武装1回につき最大1キー」に限られる。
4. **キャンセル可能区間はジョブが所有する。** マイクやミュートと同じく、処理に入るときに
   開き、`RecordingJob.run` の finally で必ず閉じる（ADR 0001 の決定2に従う）。
   フロント側の同期は投げっぱなしで、リトライも完了待ちもしない。
5. **フックは専用スレッドに、自前のメッセージループごと常駐させる。** コールバックは
   キーの判定とチャネル送信だけを行い、emit（IPC）は別スレッドに逃がす。
6. **消費するなら物理入力1回ぶんを丸ごと消費する。** 捕捉した keydown と対になる keyup も
   消費し、キーリピートは消費するが emit は増やさない。injected（合成キー）かどうかは
   問わない。

## 根拠

- 1入力＝1意味にすれば、stray なキーエッジが滑り込んでも「無視ログが出るだけ」になる。
  誤爆をガードで潰すのではなく、兼務をやめることで構造的に消す。
- キャンセルの意味を processing に限定すれば、`JobPhase` も停止シグナルの理由も増えない。
  録音中の破棄は「PTT を離して結果を捨てる」で既に足りており、それ用に脱出経路を増やすのは
  ADR 0001 が排したはずの複雑さを呼び戻す。実際、フロントの差分は分岐1つの削除と
  メソッド1つの追加が中心で、状態機械の形は変わっていない。
- **自動 disarm（決定3）が、フロント側の単純さを支えている。** フラグの解除をフロントの
  応答性に依存させると、WebView のハングやクラッシュで「Esc を永久に飲み込むトレイアプリ」
  になりうる。フック側が1キーで自己解除するなら、同期が失敗しても被害は Esc 1回の
  空振りで頭打ちになり、フロントは投げっぱなしでよくなる。
  先行実装（cda2219）にはこの同期を保証するための直列化ゲート（`cancelGate.ts`、112行＋
  テスト70行、リトライと適用待ちつき）があったが、自動 disarm があれば不要と判断して捨てた。
  ADR 0001 の教訓（非同期の面倒を状態管理に持ち込まない）をここでも適用する。
- **専用スレッド（決定5）は、フックが黙って外れるのを防ぐ。** LL フックのコールバックは
  設置したスレッドのメッセージポンプ経由で呼ばれ、応答が遅いと OS がフックを解除する。
  Tauri のメインスレッドは COM 経由のミュート（録音の開始/終了ごと）などで塞がりうるため、
  ポンプを回すだけのスレッドに隔離する。
- **物理入力1回ぶんを丸ごと消費する（決定6）のは、自動 disarm の裏返し。** disarm 後は
  リピートが素通しになるため、捕捉フラグが無いと「Esc 長押しで最初の1回だけ FreeVoice が
  食べ、残りは下のアプリに漏れる」という見える破綻になる。押下を飲むなら離上とリピートまで
  飲む、が一貫した規則。捕捉フラグが取り残された場合（ロック画面で離した等）も、次の
  keyup で必ず解除されるので被害は Esc 1回で頭打ちになる。
- injected（合成キー）の除外は**あえて行わない**。FreeVoice が合成するのは貼り付け
  （Ctrl+V／本文テキスト）だけで Esc は送らないため防ぐ対象が無く、除外すると
  スクリーンキーボード・リモートデスクトップ・キーリマッパー経由の Esc だけが
  キャンセルできなくなる。

## 影響

- 処理中のみ Esc が効く。ユーザーから見ると「オーバーレイがスピナーを出している間だけ」で、
  表示と一致する。
- 修飾キーの組み合わせ（Ctrl+Esc 等）は区別しない。処理中の1秒程度に限られ、実害は
  当該操作が1回空振りする程度のため許容する。
- セキュアデスクトップ（UAC・ロック画面）にはフックが届かないが、そこで録音操作は行わない。
- フックの設置に失敗しても Esc キャンセルが効かなくなるだけで、起動と録音は続行する。
- フックの判定は純関数（`handle_escape_keydown` / `handle_escape_keyup`）に切り出してあり、
  Windows API 無しで単体テストできる。
